## Blocker

1. **CI (`author-check`) is red on main, and ten commits carry the author `Claude <noreply@anthropic.com>`.**
   `.github/workflows/author-check.yml:25-31` fails on any commit after `.github/author-check-base:1`
   (`05df948`) whose author matches `claude|anthropic`. Five such commits are after the base: `12b47fb`, `e7bc376`,
   `52e6371`, `94b9719`, `9459928`. Five earlier ones (`57dac04`, `14a94fe`, `199c4cf`, `da166c2`, `4204be7`) were
   skipped by `9d8a70f` ("advance author-check base past known bulk-rewrite candidates"), which does not say that it
   hides AI-authored commits. This breaks CLAUDE.md rule 9 and the "red CI first" rule.
   *Fix:* history cannot be rewritten (no force-push), so the owner decides: advance the base to `12b47fb` with an
   honest message. Make sure every cloud session sets `user.name/user.email` before the first commit (a SessionStart
   hook or `.claude/settings.json`), so it does not happen again.

2. **Changing the app language on Android probably crashes (suspected, needs a 1-minute device check).**
   `MainActivityLanguage.kt:22-30` calls `activity.recreate()` on a language change, and also once on first launch if
   the DataStore language differs from the SharedPreferences copy. `recreate()` disposes `KoinApplication` and builds a
   new Koin graph. The `DataStore<Preferences>` singleton (`DataModule.kt:61-64`) has no `onClose`, and its
   `CoroutineScope(SupervisorJob() + io)` is never cancelled, so the new graph opens a second DataStore on the same
   file. DataStore 1.2.1 throws `IllegalStateException: There are multiple DataStores active for the same file` on the
   first read (the Splash reads `onboardingCompleted`). The `Databases` drivers are leaked in the same way. Before this
   change the Activity was never recreated (`configChanges` in the manifest), so the graph lived as long as the process.
   *Fix:* build the Koin graph and the DataStore once per process (Application-level Koin, or a process-wide holder) and
   do not tie them to composition. Alternatively close the scope in `onClose`. Add an instrumented test:
   change the language, then read the settings.

## Major

3. **A visible "Paylaş" button does nothing.** `ResultScreen.kt:309` (`SHARE_AVAILABLE = true`, set by `c20cec0`),

   *Fix:* back to `false` until B3 lands. The flag change was hidden in a commit about versioning.

4. **The daily goal counts forfeited, time-up and empty-wheel games, which its own KDoc and the docs exclude.**
   `DailyGoal.kt:26-27` counts every recorded session except `LEVEL_TEST`. `FinishGame` records forfeits
   (`GameViewModel.kt:536`), so answering nothing and pressing quit reaches a goal of 1. KDoc (`DailyGoal.kt:14,23`)
   says "abandoned/quit games do NOT count", and the streak uses `completed` (`UserRepositories.kt:134`), so the chip
   and the streak disagree. The test `DailyGoalTest.kt:96-103` locks in the time-up case ("counts as a completed
   wheel").
   *Fix:* ask the owner what a "çark" is. Suggestion: count `completed || reason == TIME_UP/WRONG_IN_HARDCORE` but never
   FORFEIT/EMPTY_WHEEL. That needs `reason` (or a flag) in `SessionRecord`. Then align KDoc, GAME_RULES and the test.

5. **On iOS the About screen shows a different version from the one in the store build.** `core/domain/build.gradle.kts:33-37`
   reads `lexi.versionName` from Gradle properties. `release-android.yml:84` passes `-P` from the tag, but
   `release-ios.yml:88-92,109` passes the tag only to `xcodebuild` (`MARKETING_VERSION`). The framework is built with
   plain `./gradlew :shared:linkReleaseFrameworkIosArm64` and the Xcode phase `embedAndSignAppleFrameworkForXcode`
   (`project.pbxproj:155`), so `AppInfo.VERSION_NAME` is the `gradle.properties` value (`1.0.0`, build `1`), never the
   tag. `Config.xcconfig:6-7` is also hard-coded `1.0`/`1`, which CLAUDE.md rule 10 says must not be a second source.
   *Fix:* in the iOS workflow export `ORG_GRADLE_PROJECT_lexi.versionName/versionCode` (or `-P` on the link step) from
   the same tag logic. Longer term read the version from the bundle on iOS.

6. **"Deftere ekle" can erase a card's progress.** `ResultViewModel.kt:79-90`: if `progress.get` throws, `existing`
   is `null` and a blank `CardProgress` is saved over the real row (seen/correct/wrong reset). The handler also has no
   guard for double taps (read-modify-write, `addedToNotebook` +1 each time), writes in DUEL although
   `srsExcludedModes` says duel must not touch the notebook, and accepts any `cardId`.
   *Fix:* on read failure return without saving; ignore the intent if the row is already added or the mode is
   srs-excluded; serialize with a `Mutex` or check `isAddedToNotebook`. Add the regression tests.

7. **The day-boundary code that the daily card depends on has no real test.** `SystemAppClock.msUntilNextDay`
   (`SystemAppClock.kt:27-34`) has no test at all (`SystemAppClockTest` covers only `nowMs`/`epochDay`). The "DST"
   test (`HomeViewModelTest.kt:237-246`) uses a stub clock with a fake `82_800_000 - atMs`, so it only checks
   division. Spring-forward and fall-back days (23 h / 25 h), and a zone with no local midnight, are not covered.
   `GameViewModelTest.kt` has the DAILY time limit and "no restart" tests, but nothing for `AlreadyPlayed` ->
   abandoned, a missing loader -> `Failed` (`GameViewModel.kt:323`), or that the shared seed is used.
   *Fix:* a `SystemAppClock` test with a zone-injected constructor for `Europe/Istanbul` and one DST zone; the three
   GameViewModel daily-branch tests.

8. **The onboarding level choice has no effect, and Back is not wired.** `OnboardingRepository.selectedLevel` is saved
   (`OnboardingViewModel.kt` (`PickLevel`)) but nothing reads it (no usage outside the repository and the tests), so Level
   Select still starts at A1. There is no `BackHandler`: system Back on step 2/3 leaves the app, because the
   Splash was popped; only the on-screen button sends `Back` (`OnboardingScreen.kt:407`). `Skip`/`PickLevel`
   (`OnboardingViewModel.kt` (`Skip`, `PickLevel`)) launch with no `try/catch` (a DataStore IO error crashes) and can run twice
   on a double tap, which navigates twice. The step is in the ViewModel only, so process death restarts at step 1.
   *Fix:* read `selectedLevel` as the Level Select start level (or drop the claim from the copy); add a
   `BackHandler`; guard with a `saving` flag and catch exceptions.
